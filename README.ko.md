# Karpathy에서 영감을 받은 Claude Code 가이드라인

> 새 프로젝트 [Multica](https://github.com/multica-ai/multica)를 확인해 보세요 — 재사용 가능한 스킬로 코딩 에이전트를 실행하고 관리하는 오픈소스 플랫폼입니다.
>
> X에서 팔로우하기: [https://x.com/jiayuan_jy](https://x.com/jiayuan_jy)

[Andrej Karpathy가 관찰한 LLM 코딩의 함정](https://x.com/karpathy/status/2015883857489522876)에서 도출한, Claude Code의 동작을 개선하기 위한 단일 `CLAUDE.md` 파일입니다.

[English](./README.md) | [简体中文](./README.zh.md) | 한국어

## 문제점

Andrej의 글에서:

> "모델은 사용자를 대신해 잘못된 가정을 내리고는, 확인도 없이 그대로 밀고 나간다. 자신의 혼란을 관리하지 않고, 명확히 해달라고 요청하지 않으며, 모순을 드러내지 않고, 트레이드오프를 제시하지 않으며, 반박해야 할 때 반박하지 않는다."

> "모델은 코드와 API를 과도하게 복잡하게 만들고, 추상화를 부풀리며, 죽은 코드를 정리하지 않는 것을 정말 좋아한다... 100줄이면 될 것을 1000줄짜리 부풀려진 구조로 구현한다."

> "여전히 가끔은 충분히 이해하지 못한 주석과 코드를, 작업과 무관함에도 부수 효과로 변경하거나 제거한다."

## 해결책

이러한 문제를 직접적으로 다루는 네 가지 원칙을 하나의 파일에 담았습니다:

| 원칙 | 다루는 문제 |
|-----------|-----------|
| **코딩 전에 생각하기 (Think Before Coding)** | 잘못된 가정, 숨겨진 혼란, 누락된 트레이드오프 |
| **단순함 우선 (Simplicity First)** | 과도한 복잡화, 부풀려진 추상화 |
| **외과적 변경 (Surgical Changes)** | 무관한 수정, 건드리면 안 되는 코드 건드리기 |
| **목표 주도 실행 (Goal-Driven Execution)** | 테스트 우선, 검증 가능한 성공 기준을 통한 레버리지 |

## 네 가지 원칙 상세

### 1. 코딩 전에 생각하기

**가정하지 말 것. 혼란을 숨기지 말 것. 트레이드오프를 드러낼 것.**

LLM은 흔히 한 가지 해석을 조용히 골라 그대로 밀고 나갑니다. 이 원칙은 명시적 추론을 강제합니다:

- **가정을 명시적으로 진술하라** — 불확실하면 추측하지 말고 물어라
- **여러 해석을 제시하라** — 모호함이 있을 때 조용히 하나만 고르지 마라
- **타당할 때 반박하라** — 더 단순한 접근법이 있다면 말하라
- **혼란스러우면 멈춰라** — 무엇이 불명확한지 짚고 명확히 해달라고 요청하라

### 2. 단순함 우선

**문제를 푸는 최소한의 코드. 투기적인 것은 없게.**

과잉 설계 경향에 맞섭니다:

- 요청받지 않은 기능은 추가하지 않는다
- 일회성 코드에 추상화를 두지 않는다
- 요청받지 않은 "유연성"이나 "구성 가능성"은 넣지 않는다
- 일어날 수 없는 시나리오에 대한 오류 처리는 하지 않는다
- 200줄을 50줄로 줄일 수 있다면, 다시 작성하라

**판단 기준:** 시니어 엔지니어가 보면 과하게 복잡하다고 할까? 그렇다면 단순화하라.

### 3. 외과적 변경

**꼭 필요한 것만 건드려라. 네가 어지른 것만 치워라.**

기존 코드를 편집할 때:

- 인접한 코드, 주석, 포맷을 "개선"하지 마라
- 망가지지 않은 것을 리팩토링하지 마라
- 다르게 하고 싶더라도 기존 스타일에 맞춰라
- 무관한 죽은 코드를 발견하면, 삭제하지 말고 언급하라

변경으로 인해 고아(orphan)가 생기면:

- 네 변경으로 인해 사용되지 않게 된 import/변수/함수를 제거하라
- 요청받지 않은 한, 기존부터 있던 죽은 코드는 제거하지 마라

**판단 기준:** 변경한 모든 줄은 사용자의 요청으로 직접 추적될 수 있어야 한다.

### 4. 목표 주도 실행

**성공 기준을 정의하라. 검증될 때까지 반복하라.**

명령형 작업을 검증 가능한 목표로 변환하라:

| 이렇게 말하는 대신... | 이렇게 변환하라... |
|--------------|-----------------|
| "유효성 검사를 추가해" | "잘못된 입력에 대한 테스트를 작성한 뒤, 통과하게 만들어" |
| "버그를 고쳐" | "버그를 재현하는 테스트를 작성한 뒤, 통과하게 만들어" |
| "X를 리팩토링해" | "리팩토링 전후로 테스트가 통과하는지 확인해" |

여러 단계의 작업에는 간단한 계획을 진술하라:

```
1. [단계] → 검증: [확인 항목]
2. [단계] → 검증: [확인 항목]
3. [단계] → 검증: [확인 항목]
```

강한 성공 기준은 LLM이 독립적으로 반복하게 해줍니다. 약한 기준("작동하게 만들어")은 끊임없는 추가 설명을 요구합니다.

## 설치

**옵션 A: Claude Code 플러그인 (권장)**

Claude Code 안에서, 먼저 마켓플레이스를 추가합니다:
```
/plugin marketplace add forrestchang/andrej-karpathy-skills
```

그런 다음 플러그인을 설치합니다:
```
/plugin install andrej-karpathy-skills@karpathy-skills
```

이렇게 하면 가이드라인이 Claude Code 플러그인으로 설치되어, 모든 프로젝트에서 스킬을 사용할 수 있습니다.

**옵션 B: CLAUDE.md (프로젝트별)**

새 프로젝트:
```bash
curl -o CLAUDE.md https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md
```

기존 프로젝트(이어 붙이기):
```bash
echo "" >> CLAUDE.md
curl https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md >> CLAUDE.md
```

## Cursor에서 사용하기

이 저장소에는 커밋된 Cursor 프로젝트 규칙([`.cursor/rules/karpathy-guidelines.mdc`](.cursor/rules/karpathy-guidelines.mdc))이 포함되어 있어, Cursor에서 프로젝트를 열면 동일한 가이드라인이 적용됩니다. 설정 방법, 다른 프로젝트에서 규칙 사용하기, Claude Code와의 관계는 **[CURSOR.ko.md](CURSOR.ko.md)**를 참고하세요.

## 핵심 통찰

Andrej의 말:

> "LLM은 구체적인 목표를 만족할 때까지 반복하는 데 유독 능하다... 무엇을 하라고 말하지 말고, 성공 기준을 주고 알아서 하게 두어라."

"목표 주도 실행" 원칙이 바로 이것을 포착합니다: 명령형 지시를 검증 루프가 있는 선언형 목표로 변환하는 것.

## 잘 작동하고 있는지 아는 법

이 가이드라인이 작동하고 있다면 다음이 보일 것입니다:

- **diff에 불필요한 변경이 줄어듦** — 요청한 변경만 나타남
- **과도한 복잡화로 인한 재작성이 줄어듦** — 처음부터 코드가 단순함
- **구현 전에 명확화 질문이 나옴** — 실수 후가 아니라
- **깔끔하고 최소한의 PR** — 지나가다 하는 리팩토링이나 "개선"이 없음

## 커스터마이징

이 가이드라인은 프로젝트별 지침과 병합하도록 설계되었습니다. 기존 `CLAUDE.md`에 추가하거나 새로 만드세요.

프로젝트별 규칙은 다음과 같은 섹션을 추가하세요:

```markdown
## 프로젝트별 가이드라인

- TypeScript strict 모드를 사용한다
- 모든 API 엔드포인트는 테스트가 있어야 한다
- `src/utils/errors.ts`의 기존 오류 처리 패턴을 따른다
```

## 트레이드오프 노트

이 가이드라인은 **속도보다 신중함** 쪽으로 치우쳐 있습니다. 사소한 작업(단순 오타 수정, 명백한 한 줄 변경)에는 판단력을 발휘하세요 — 모든 변경에 전체 엄격함이 필요한 것은 아닙니다.

목표는 사소한 작업을 느리게 만드는 것이 아니라, 사소하지 않은 작업에서 값비싼 실수를 줄이는 것입니다.
